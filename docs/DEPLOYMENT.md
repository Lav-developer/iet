# Deployment, backup and handover runbook

This candidate is not an institutional production deployment. IET / DSMNRU should own the repository, domain, PostgreSQL instance, object-storage account, secrets and administrator roster before launch.

## Production prerequisites

- Node.js version supported by the lockfile and a process manager or institution-approved container platform.
- PostgreSQL with TLS, automated backups and a separate migration credential.
- Institution-owned S3-compatible object storage with bucket versioning/retention as required by policy.
- HTTPS at the reverse proxy; the application must receive the original host and scheme in trusted `Host` / forwarded headers.
- A secret manager for `DATABASE_URL`, `AUTH_SECRET`, storage credentials and any approved mail/analytics settings.
- An operational owner for content approval, security incidents, backup restoration and access review.

Production refuses to start when `DATABASE_URL`, a 32-character minimum `AUTH_SECRET`, `NEXT_PUBLIC_SITE_URL`, or the S3-compatible storage settings are missing. The file-backed content store, demo authentication and local upload adapter are development-only paths.

## First deployment

1. Create the database and an application role with only the permissions required by Prisma at runtime. Keep migration privileges separate where possible.
2. Create a private object-storage bucket and a service account restricted to that bucket. Enable encryption, versioning and lifecycle rules approved by the institution.
3. Configure every production variable from `.env.example` in the secret manager. Use a random secret generated by the secret manager; do not reuse a development secret.
4. Install from the lockfile and generate the Prisma client:

   ```bash
   npm ci
   npm run db:generate
   ```

5. Apply checked-in migrations before starting the web process:

   ```bash
   npx prisma migrate deploy
   ```

   Migrations currently include the normalized schema, shared rate-limit buckets, session-version invalidation, publication department ownership and editorial attribution.

6. Do **not** run `prisma/seed.ts` against production. Create the first named `SUPER_ADMIN` or `IET_ADMIN` through a controlled bootstrap procedure, then create additional named accounts in `/admin/users`.
7. Build and start:

   ```bash
   npm run build
   npm run start
   ```

8. Put the process behind an HTTPS reverse proxy. Set the proxy's trusted forwarded-header behavior deliberately; never accept arbitrary client-supplied IP headers as an identity signal.
9. Perform the smoke checks in the release checklist below, including a failed configuration test in a non-production environment.

## Configuration and access controls

- `AUTH_SECRET` rotation invalidates every JWT. Plan a maintenance window, replace the secret, restart all instances and require all administrators to sign in again.
- A user password, role, department scope, active state or explicit deactivation increments `User.sessionVersion`; existing tokens stop working on the next request.
- Use one account per person. Review the user list and department assignments at least quarterly and after staff changes.
- `DEPARTMENT_ADMIN` is checked against both the record currently addressed and the requested department, including normalized faculty/laboratory/author relationships.
- Keep `SUPER_ADMIN` rare. IET administrators cannot grant super-administrator access.
- Production rate limits use PostgreSQL so multiple application instances share counters. Add alerting for repeated login failures and unusual admin mutation volume.
- The current same-origin policy rejects state-changing requests without a matching `Origin`/`Referer` in production. Keep the reverse proxy host configuration stable and test approved administrative origins.

## Object storage and uploads

The upload path accepts only approved image types or PDF documents, enforces size limits, checks magic bytes and records object keys plus editorial metadata in PostgreSQL. The application media route:

- looks up the object in the approved database record;
- exposes only published documents;
- sets `nosniff`, a restrictive CSP and safe content disposition;
- never trusts a user-supplied filesystem path.

Before launch, the institution should add or verify malware scanning, image dimension/metadata policy, object lifecycle/retention, access logging and a tested restore path. If restricted documents are introduced, replace public application URLs with short-lived signed URLs and add authorization checks to the download route.

## Backup and recovery

### PostgreSQL

- Take automated encrypted backups according to the institutional retention policy; enable point-in-time recovery if the managed service supports it.
- Keep at least one backup in a separate account or region approved by the institution.
- Include the Prisma migration history and record the application release associated with each backup.
- Test restoration on an isolated database at least quarterly. Verify users, workflow states, audit logs, relationships and publication department ownership.
- After a restore, rotate credentials if the recovery environment exposed them and verify `AUTH_SECRET`/storage access before traffic is restored.

A basic non-production logical backup example is:

```bash
pg_dump --format=custom --file=iet-$(date +%Y%m%d).dump "$DATABASE_URL"
pg_restore --list iet-YYYYMMDD.dump
```

Use the institution's encrypted backup service rather than storing dumps in the repository or public object bucket.

### Object storage

Enable provider versioning or replication as approved. Back up object metadata through PostgreSQL and verify that every referenced key exists. Test restoring a representative image and PDF, including MIME metadata, title, alt text and status. Do not copy production objects into a developer-owned account.

## Release checklist

- [ ] `npm ci`, `npm run db:generate`, `npx prisma migrate deploy`, `npm run build` succeed in the release environment.
- [ ] App refuses to start in a disposable production-mode test when a required variable is removed.
- [ ] Public homepage, department, programme, research, resources, sitemap and robots routes return successfully.
- [ ] `/api/search?q=engineering` returns only approved published records and rate-limits repeated requests.
- [ ] Login rejects invalid credentials, rate-limits attempts, sets an HTTP-only cookie and does not expose credential details.
- [ ] Logout removes the cookie; deactivating a test account invalidates an already-issued session.
- [ ] Editor cannot publish/archive; department admin cannot read or mutate another department; cross-department relationship IDs are rejected.
- [ ] Upload rejects spoofed MIME/magic bytes, oversized files and missing image alt text; PDF downloads use attachment disposition.
- [ ] Security headers, HTTPS redirect/proxy behavior, error pages and log redaction are checked externally.
- [ ] Keyboard-only, focus, responsive, reduced-motion, contrast/text-size and screen-reader smoke checks pass.
- [ ] Content owners approve every factual record against `docs/CONTENT-VERIFICATION.md`.

## Handover package

Transfer these items to IET / DSMNRU through approved channels:

- repository and branch ownership;
- `.env.example` plus secret-manager variable names, never secret values;
- Prisma schema and all migrations;
- object-storage bucket policy and lifecycle configuration;
- backup/restore evidence and escalation contacts;
- named administrator roster and role/department assignments;
- content verification queue and publication approval policy;
- accessibility, privacy, analytics and retention decisions;
- incident response and credential-rotation contacts;
- this runbook and the final acceptance-test record.
